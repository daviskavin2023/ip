# 3040-穿透优选-tunnel (Cloudflare Tunnel 智能优选与高可用调度中心)
## 业务需求说明书 (PRD - Product Requirements Document)

---

## 1. 文档概述

### 1.1 项目背景与网络现状
目前家庭内部署了诸多核心业务系统（如 3012 百果园财务、进销存、自动化脚本等）。家庭宽带无公网 IPv4，仅有公网 IPv6。
- **关于 80/443 入站现状（事实核定）**：已知前期审计中，家庭本地网关（`.15`）自身的防火墙规则（`fw4 forward=REJECT`，仅放行 ICMPv6）存在入站拦截。在本地网关防火墙彻底放行并实测之前，运营商骨干网是否封锁 80/443 尚属“待打开本地防火墙后实测确认”状态，而非既定定论。
- **关于公网 IPv4 穿透**：由于外网移动网络与办公网络存在大量纯 IPv4 场景，现有方案通过部署在 PVE10 CT160（`10.10.10.160`）上的 Cloudflare Tunnel (`cloudflared`) 进行反代穿透暴露到公网（如 `bgy.808608.xyz`）。然而，Cloudflare 默认的 Anycast 调度将国内请求路由至美国或欧洲节点，导致：
  - **物理延迟高**（250ms ~ 350ms）
  - **丢包率高**（晚高峰达 15% ~ 30%）
  - **国内运营商对 UDP 协议（QUIC）严重 QoS 干扰**，页面加载迟钝甚至连接中断。

### 1.2 核心目标
构建一个自建、轻量、高可用、可视化的 **Cloudflare Tunnel 智能优选与接入调度平台 (3040-tunnel)**。在完全保持现有业务域名、不破坏现有域名其他子域解析、无缝兼容未来新业务的前提下，实现外网访问延迟降至 **40ms ~ 80ms**、丢包率接近 **0%**、具备故障自动逃生的高可用架构。

## 2. 核心设计原则与业务边界

### 2.1 铁律与约束
1. **外部访问体验零感知迁移**：
   - 现有正式业务域名（例如 `bgy.808608.xyz`）**完全不变**，不加端口号（标准 `https://` 443 端口），对外使用方式完全一致。
2. **域名无害化与精确接管 (SaaS 隔离)**：
   - 主域名 `808608.xyz` 承载多项其他业务（如外部服务器、第三方邮箱、其他公网服务）。
   - **绝对禁止全域接管或改动非本项目相关的二级域名**。
   - 采用 **Cloudflare for SaaS (Custom Hostnames)** 技术，仅对注册的特定业务二级域名进行回退源绑定与定向加速，其他二级记录完全独立不受干扰。
3. **与 `cloudtunnel.808608.xyz` 面板务实联动（杜绝凭空假设）**：
   - 经实地核查：`cloudtunnel.808608.xyz` 部署于 CT160（`10.10.10.160:39091`），其核心入口为 `/opt/tunnel-panel/tunnel-panel.py`，工作区内暂无独立编号。
   - **绝不能凭空假设其具备现有 webhook 接口**。
   - **联动落地方案**：必须先只读审计 `tunnel-panel.py` 的源码实现。优先采用“3040 监听其配置/数据库文件变动”，或“在 `tunnel-panel.py` 保存处安全追加一条极简通知钩子”，实现用户依然只需在面板点【保存】，后续 Cloudflare SaaS 注册与 DNS 更新全自动触发。
4. **结合 10.10.10.4 内网 DNS (AdGuardHome) 实现内外双面神分流 (Split-Horizon DNS)**：
   - 杜绝家庭内网访问公网域名的“发夹弯（Hairpinning）绕路”浪费带宽与增加延迟；
   - **人在家里**：向 `10.10.10.4` 查询，秒级解析至 Lucky 内网网关（`10.10.10.5`），直通千兆内网，享受 **1ms 极速延迟**；
   - **人在外网**：向公共 DNS 查询，解析至 **Cloudflare 亚太最优 IP**，享受 **40~70ms 高速穿透**。
5. **高扩展性与模板化**：
   - 未来新增任何项目反代（如新增 3041、3042 等），只需在面板声明，即可自动纳入优选与监控池，无需重复开发。
6. **测速环境真实性前提验证**：
   - 测速引擎部署于 CT160。**实施前提必须先实地验证 CT160 的出网路由**，确保其走的是家庭宽带真实物理出口，绝不能被旁路由代理（daed/mihomo）劫持，否则测速数据无效。
7. **绝对高可用、抖动抑制与零断联兜底**：
   - 建立主动健康检查（Active Healthcheck）机制与**坏 IP 冷却拉黑（熔断器模式）**，避免坏 IP 与好 IP 间频繁抖动。
   - 充分考虑 DNS 提供商免费版 TTL 限制（如 600s），采用“双优选 IP 并行轮询”与官方 Anycast 线路保底，杜绝业务断联。

### 3.2 10.10.10.5 Lucky (CT105) 的协同角色定位

1. **内网统一着陆点 (Internal Ingress Gateway)**：
   - 当人在家里 Wi-Fi 访问公网域名时，`10.10.10.4` AdGuardHome 统一将请求重写到 **`10.10.10.5` (Lucky)**。
   - Lucky 根据 HTTP 请求的 Hostname（如 `bgy.808608.xyz`）在局域网内进行二次精准反代分流，免去为每个项目在 AdGuardHome 维护不同内网 IP 的麻烦。
2. **Tunnel 业务反代中枢 (Decoupled Backend)**：
   - CT160 的 `cloudflared` 可以将请求无缝对接给 `10.10.10.5` Lucky，由 Lucky 统一管理内网路由、路径重写与 Header 过滤。
3. **IPv6 DDNS 与 IPv4 优选的合流中枢**：
   - 对于需要同时具备“IPv6 直连 + IPv4 Tunnel 优选”的高吞吐服务（如大文件下载/NAS 相册），Lucky 负责维护公网 IPv6 DDNS（AAAA 记录），3040 负责维护 IPv4 优选 IP（A 记录），两者互补共赢。

### 3.4 关键技术点与前置可行性约束

#### 1. 协议栈加固 (规避运营商 QoS)
- 强制本地 `cloudflared` 连接协议为 `protocol: http2`（纯 TCP 握手），替换默认的 QUIC (UDP)，彻底避免国内 ISP 对 UDP 443 的恶性丢包。
- 启用 `ha-connections: 4`，与 Cloudflare 边缘建立多路长连接复用池。

#### 2. Cloudflare for SaaS 套餐与费用门槛说明
- **官方资费政策**：Cloudflare 自 2021 年起，针对免费版账户（Free Plan）提供 **前 100 个 Custom Hostnames（自定义主机名）免费额度**（超出部分 $0.10/个/月）。
- **必须注意的硬性前置门槛**：虽然在免费额度内，但 Cloudflare 强制要求**账户必须绑定有效的国际支付方式（PayPal 或信用卡）**以完成开通验证。在实施 Phase 1 之前，必须先在 Cloudflare 仪表盘确认该前置条件已就绪。
- 将已绑好 Tunnel 的专用内部域名（如 `tunnel-origin.808608.xyz`）设为 **回退源 (Fallback Origin)**。
- 业务域名 `bgy.808608.xyz` 添加为 **Custom Hostname**，由 Cloudflare 自动签发并维护权威 TLS 证书。

#### 3. 本地自建优选引擎与出网环境核验
- 采用开源最权威测速核心：**[XIU2/CloudflareSpeedTest](https://github.com/XIU2/CloudflareSpeedTest)**。
- **出网前置检查（只读验证）**：在 CT160 部署测速前，必须先执行 `ip route`、`traceroute 1.1.1.1` 及 `curl cip.cc`，实测确认 CT160 走的是直连家庭宽带的真实物理出口，绝未被旁路由（daed/mihomo）代理，避免测出“虚假优选”。

#### 4. DNS 动态调度器、TTL 现实约束与分线路成本门槛
- **免费版 DNS 的 TTL 现实**：
  - 腾讯云 DNSPod 免费版最低 TTL 为 **600s（10分钟）**；
  - 阿里云 DNS 免费版最低 TTL 亦为 **600s**；
  - 故在免费版 DNS 下，单靠修改 A 记录无法达到纯客户端维度的秒级切换（因本地系统与运营商递归 DNS 会缓存 600s）。
- **双重加速与容灾设计（破解 TTL 限制）**：
  - **策略 A（多 A 记录并发）**：在 DNS 中同时配置 2 个健康度最高的优选 IP。当首选 IP 偶发失联时，现代客户端/浏览器通常会在数百毫秒内重试下一个 A 记录，平滑处理单点抖动；
  - **策略 B（自动降级切换）**：DNS 调度器在检测到 IP 故障后立即推送 API 更新（TTL 设为最低允许值 600s），保证故障影响窗口收敛在最低周期内。
- **分线路解析（智能模式）的成本门槛**：
  - “分运营商匹配专属 IP（电信/联通/移动分流）”要求 DNS 服务商支持分线路解析。在腾讯云 DNSPod 或阿里云，分线路解析通常为付费版/特定套餐功能，免费版仅支持“默认”全网线路。
  - **落地方案**：Phase 0 需核实当前 DNS 套餐。若为免费版，优先采用“全局双优选 A 记录”平替，避免依赖未购付费功能。

### 3.5 【2026-09-27 复核】当前生产实际链路与 Roadmap 的偏差说明

本节由第三方复核（只读实测，未做任何改动）写入，目的是让 PRD 文字与线上真实状态保持一致，避免后续接手者被文档带偏。

**实测方法**：家庭内网对 UDP 53 端口做了强制 DNS 劫持（不论指定查哪个服务器都会被重写），因此改用 DoH（443 端口）分别问 `1.1.1.1` 与 `8.8.8.8` 两个独立公共解析器，交叉验证一致。

**实测到的真实解析链**（与本节以上描述的 Custom Hostname 方案不同）：
```
bgy.808608.xyz  --CNAME(仅DNS/灰云,非Cloudflare代理)-->  speed.808608.xyz
speed.808608.xyz --NS委托--> ns1/ns2.alidns.com（阿里云智能解析，分线路）
    ├─ 境外线路 --CNAME--> origin.kavin.fun --A--> Cloudflare 代理 IP（兜底/默认站点）
    └─ 默认(境内)线路 --A(多条并发)--> 候选池优选 IP（daemon.py 维护的 5 个 /16 节点）
```
**实测生产健康度**：用与家庭网络完全无关的外部浏览器环境直接访问 `https://bgy.808608.xyz`，**页面正常加载出真实业务内容**（"百果园现金对账 v2.4.17"，星汇品峰店当日流水数据），说明当前这条链路是**真实生效、生产可用**的，不是纸面设计。控制台有一条 `An unknown error occurred when fetching the script` 的报错，来源未查（可能是前端某个静态资源，也可能与本项目无关），建议后续留意但不算阻断。

**与本 PRD 第 3.4 节及第 6 章 Roadmap 的偏差**：
- 第 3.4 节第 2 点与第 6 章 Phase 1 的全部步骤，描述的是"走 Cloudflare for SaaS Custom Hostname"这条路径；但实测线上走的是"**阿里云 NS 委托 + 分线路解析**"这条路径，`bgy.808608.xyz` 本身的 Cloudflare 记录从"代理(橙云)CNAME 到 `cfargotunnel.com`"变成了"仅 DNS(灰云)CNAME 到 `speed.808608.xyz`"——这是一次**实际已发生但未回写进本 PRD 的架构变更**。
- 代码侧（`src/cf_client.py`、`src/daemon.py`）目前只在断路器兜底时才调用 Cloudflare API（删记录+建回 Tunnel CNAME），日常轮询/切换全部通过 `src/aliyun_client.py` 操作阿里云 DNS，**没有任何一行代码真正调用了 Custom Hostname / SSL for SaaS 相关接口**。`docs/phase0-baseline-report.md` 记录的"CF Token 缺少 Custom Hostname 权限，403"这一阻断项，后续看不出有被解决的痕迹——大概率是绕开了这条路径，而不是解决了它。
- **建议**：这个架构切换如果是团队/上一位协作者刻意的决定（用阿里云分线路替代 SaaS，省掉了权限门槛和潜在费用），应该在这里正式确认并把第 3.4 节第 2 点、第 6 章 Phase 1 的步骤改写成"阿里云 NS 委托方案"，Custom Hostname 那条路径整体标记为"已放弃/备选"，避免以后又有人照着 Phase 1 的旧步骤去重复申请 Custom Hostname 权限。这一点需要人工确认，本次复核不擅自替换 Roadmap 正文。

## 4. 功能模块详述

### 模块一：域名与隧道管理中心 (Domain & Tunnel Manager)
1. **多域名纳管**：
   - 列表管理受加速保护的域名（如 `bgy.808608.xyz`）。
   - 新增域名向导：输入新域名、自动生成 Cloudflare for SaaS 验证指引、绑定统一 Fallback Origin。
2. **状态感知**：
   - 实时检测域名的 SSL/TLS 证书就绪状态、DNS 生效状态、回源可达性状态。

### 模块二：智能测速与网络优化引擎 (Speedtest Engine)
1. **自动化定时调度**：
   - 支持 Cron 周期测速（默认每 2 小时测速一次，可自定义）。
2. **环境自适应参数配置**：
   - 最大允许延迟阈值（如 `< 100ms`）。
   - 丢包率容忍阈值（默认 `0%` 丢包）。
   - 并发测速线程数、下载测速数据量（避免占用家庭带宽过多）。
3. **测速历史与节点大盘**：
   - 记录测速结果，包含节点国家/城市代码（HKG、NRT、ICN、SJC 等）、平均延迟、实时吞吐。

### 模块三：DNS 自动同步与分流策略 (DNS Sync Dispatcher)
1. **自动推送**：
   - 测速完成后，提取优质 IP 自动调用 DNS API 更新 A 记录。
2. **多线路细分**：
   - 默认模式：全网统一最优 IP（双优选 A 记录并行）。
   - 智能模式：分运营商（电信 / 联通 / 移动 / 海外）匹配专属优质 IP。

### 模块四：高可用容灾、熔断与防抖动机制 (High Availability & Failover)
1. **高频轻量巡检心跳**：
   - 每 1~3 分钟对当前在线的优选 IP 发起一次轻量 TCP 443 + HTTP HEAD 健康检查。
2. **坏 IP 冷却拉黑与抖动抑制（Circuit Breaker 熔断器机制）**：
   - 若某个优选 IP 在巡检中心跳连续失败 **3 次**，立即将其标记为“不可用”，并打入**冷却黑名单（惩罚期默认 2 小时）**；
   - 在冷却期内，该 IP 即使在测速报告中延迟较低，也绝不选入生产解析列表，彻底避免因偶发波动在坏 IP 与好 IP 之间来回震荡切线。
3. **分级降级熔断策略**：
   - **一级故障（当前优选 IP 丢包/超时）**：立即无缝切换至同批次候选的备用优选 IP；
   - **二级故障（备选优选 IP 均不可用）**：切换到内置的“白名单长期稳定 Anycast 节点”或公共智能优选 CNAME；
   - **终极熔断（外部节点全网异常）**：自动将解析重置为 Cloudflare 官方默认 CNAME，确保 Tunnel 业务永不中断。

### 模块五：可视化运维控制台 (Web UI - 遵照 yulaiwo-ui 规范)

### Phase 5：【2026-09-27 定稿】cloudtunnel 面板全部域名自动接入优选 (全自动扩容)

> 本节替换掉旧版"Cloudflare for SaaS Custom Hostname"路线——已证实实际可行路径是**共享加速域名**方案（见下方 5.0），不需要 Custom Hostname、不需要每个项目单独建域名/单独跑 daemon。

**目标**：`cloudtunnel.808608.xyz` 面板管理的全部现有 Hostname（当前47个左右，数量会变）自动接入优选，**新增的 Hostname 也自动接入，不需要人工在3040这边再配置一次**。

#### 5.0 架构设计：共享加速域名

只需要一个共享的 `edge.808608.xyz`（复用现有 `speed.808608.xyz` 那套阿里云 NS 委托 + 优选IP维护机制，把域名从项目专属改成全局共享），daemon 持续维护它的优选IP池。**每个业务域名接入优选 = 把它的 CNAME 从 `<tunnel-id>.cfargotunnel.com` 改成指向 `edge.808608.xyz`**，不需要新建域名、不需要新跑一套daemon、不需要 Custom Hostname。

依据：已验证 Cloudflare 边缘IP按 SNI/Host 路由，同一个IP能同时正确服务多个不同的业务域名，前提是这台边缘机器确实部署了 `808608.xyz` 这个 zone 的证书（已实测发现：不是所有边缘IP都部署了任意zone的证书，这也是"优选"要解决的真正问题——见 VERSION.md 2026-09-27 关于 `104.21.35.165` "handshake failure" 的诊断）。

> **最终澄清（2026-09-27，已用实测验证，替换掉之前所有中间结论）**：以上说的是**zone级别**的证书覆盖差异，是真实存在的。但**同一个zone内部、不同子域名之间**共用同一张通配符证书（`CN=808608.xyz`），不存在"这个IP认`bgy`、不认`fn`"这种情况。
>
> **真正的根因，也是`bgy`能用、其他域名一直失败的核心原因**：`bgy.808608.xyz`被注册成了`kavin.fun`这个zone上的 **Cloudflare for SaaS Custom Hostname**（可在Cloudflare后台`kavin.fun`域名 → SSL/TLS → Custom Hostnames 里看到，状态`active`），其他域名都没注册。Cloudflare规定：**域名必须先把CNAME切到SaaS zone（即`speed.808608.xyz`），Custom Hostname才能验证通过**——顺序反了会一直报`"custom hostname does not CNAME to this zone"`。中间排查时怀疑过的"CT160资源不足"、"curl请求触发机器人检测"、"某个具体IP有问题"，全部已用对照实验证伪，跟这次故障无关。详见VERSION.md「[根因确认]」条目。

#### 5.1 发现机制
新增 `sync_hostnames.py`：定期（10分钟一次，systemd timer）调用 `cloudtunnel` 面板已有的 `/api/cache`（或 `/api/force-refresh`）接口拉取全量 Hostname 列表（已验证可用，无需认证）。

#### 5.2 转换与自愈逻辑
对每个 Hostname：
1. **排除名单检查**：跳过 `cloudtunnel.808608.xyz` 本身（转了会连管理后台都进不去），以及任何当前 CNAME 不是标准 `*.cfargotunnel.com` 格式的记录（说明是别人手动配置过的特殊记录，不碰）。**用户确认：除 `cloudtunnel.808608.xyz` 自身外，暂无其他排除项。**
2. **逐域名验证**：用当前生效的优选IP，对这个具体域名实测一次真实HTTPS（复用 `verify_stable`），确认这台边缘机器确实部署了它的证书，验证通过才转换；不通过则跳过、记录到"待人工确认"日志，不静默处理。
3. **转换**：调 Cloudflare API 把该 Hostname 的记录从直连 `cfargotunnel.com` 改成 CNAME 到 `edge.808608.xyz`，记录进 `managed_hostnames.json`（含原始CNAME值，供人工排查用，**不做自动化单独回滚**——用户确认全局回滚已够用）。
4. **自愈**：每轮不只检查"域名是否已转换"，还检查"当前CNAME是不是被面板自己的『强制同步Cloudflare』或手工编辑重置回了`cfargotunnel.com`"，是则自动重新转换——不需要改 `tunnel-panel.py` 一行代码。

#### 5.3 落地顺序（用户已确认：先完善本节PRD，再写代码）
1. 先在 Cloudflare 上把现有 `speed.808608.xyz` 平滑过渡/重命名为通用的 `edge.808608.xyz`（或直接新建，`bgy` 逐步切过去）。
2. 写 `sync_hostnames.py`，**先跑 Dry-run 模式**（只打印"会对哪些域名做什么改动"，不真的调用 Cloudflare API），人工核对输出无误后再解除限制。
3. 解除 Dry-run，接入 `sync-hostnames.timer`（10分钟一次）。
4. 观察至少 24 小时，确认新增/编辑 Hostname 时自动接入正常、自愈逻辑正常触发。

#### 5.4 可视化面板（沿用既有设计）

**验收标准**：新增 Hostname 全自动闭环（面板保存后10分钟内自动验证+接入或明确标记待确认）；面板自己的同步操作不会打断已生效的优选配置。
