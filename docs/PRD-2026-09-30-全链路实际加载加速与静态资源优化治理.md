# PRD-2026-09-30 全链路实际加载加速与静态资源优化治理方案
## (面向 3040 穿透优选与 3017 ylwjhfx 等业务系统的 Web 传输提速专项)

---

## 1. 为什么做（痛点背景与实测实证）

### 1.1 现状与矛盾
在 3040 项目中，通过 Cloudflare for SaaS + 阿里云智能分线路解析 + 亚太 Anycast 优选 IP 池，我们已将外网到边缘的 **TCP 握手延迟压降至 25ms~28ms**。
然而，在真实外网（手机 4G/5G 或办公网络）访问 `https://ylwjhfx.808608.xyz` 等系统时，用户端依然感知到 **2.5 秒 ~ 3.5 秒的白屏或首屏迟钝**。

### 1.2 实测数据实证（为什么不能只看延迟，要看实际加载）
2026-09-27 针对 `ylwjhfx.808608.xyz` 真实全链路压测数据揭示了首屏迟钝的真正元凶：

| 资源项 | 物理体积 | 当前压缩状态 | 当前缓存头 (Cache-Control) | 每次请求传输方式 | 实测单项耗时 |
| :--- | :---: | :---: | :---: | :---: | :---: |
| **HTML 入口 (`/`)** | 101.8 KB | 未压缩 | `no-cache, no-store, max-age=0` | 穿透 Argo 回源拉取 | 800ms ~ 1060ms |
| **样式文件 (`style.css`)** | 417.7 KB | 未压缩 | **无 Cache-Control** (0 缓存) | 穿透 Argo 回源拉取 | 850ms ~ 1270ms |
| **ECharts 引擎 (`echarts.min.js`)** | 998.9 KB | 未压缩 | **无 Cache-Control** (0 缓存) | 穿透 Argo 回源拉取 | 760ms ~ 1014ms |
| **业务脚本 (`app.js`)** | 764.8 KB | 未压缩 | **无 Cache-Control** (0 缓存) | 穿透 Argo 回源拉取 | 680ms ~ 1208ms |
| **合计首屏静态包** | **~2.38 MB** | **全部明文直传** | **全部无法复用缓存** | **每次刷新全量穿透** | **累积 2.4s ~ 3.6s** |

### 1.3 根因剖析
1. **体积过大且未压缩**：单是 `echarts.min.js` (1.0MB) 与 `app.js` (765KB) 两项就占据了 1.76 MB。由于后端（Uvicorn / Lucky）未开启 Gzip/Brotli 压缩，全部以原始文本穿透回源。
2. **0 缓存导致无用穿透**：静态资源未声明 `Cache-Control: public, max-age=...`，导致 Cloudflare 边缘节点与用户本地浏览器每次刷新都必须跨越 Argo 隧道（单向耗时 ~400ms）向家庭 CT160 回源重新下载 2.38MB。
3. **挤占家庭宽带上行**：家庭宽带上行带宽有限（通常仅 30~50 Mbps），若多人同时访问或频繁刷新，2.38MB 的大包传输极易引起拥塞和丢包，将原本 25ms 的优选链路拖慢至数秒。

## 2. 核心原则与安全红线（是否影响原项目？）

### 2.1 四大绝对铁律（零破坏性承诺）
1. **铁律一：动态 API 接口绝对不缓存（100% 实时）**：
   - 所有的 `/api/...`（包括经营日报、对账、采购单、现金流等动态数据接口）**严格维持 `Cache-Control: no-store`**。
   - 严禁对任何包含业务数据的 GET/POST 接口进行边缘或浏览器缓存，确保财务与业务数据 100% 实时准确。
2. **铁律二：HTML 入口绝对不强缓存（100% 即时发版）**：
   - `index.html` 页面必须继续保持 `Cache-Control: no-cache, no-store, must-revalidate, max-age=0`。
   - 用户每次打开或刷新页面，浏览器必须重新向服务器校验 HTML，确保发版后新逻辑秒级触达。
3. **铁律三：解压缩机制对业务代码 100% 透明**：
   - Gzip 属于 HTTP/1.1 标准协议层机制，由服务器传输前压缩，浏览器内核底层网络栈自动解压。
   - 业务层 JavaScript 代码、DOM 结构、Vue/React/原生交互、图表渲染接收到的数据与明文完全一致，**0 逻辑兼容风险**。
4. **铁律四：内网 Split-Horizon DNS 极速通道不受丝毫影响**：
   - 家庭内网环境下，通过 `10.10.10.4` AdGuardHome 解析到 `10.10.10.5` Lucky 直连，继续享受 1ms 延迟与毫秒级加载。

### 2.2 防范“发版后浏览器死活读旧缓存”的闭环机制
- **版本号指纹防击穿 (Cache-Busting)**：
  - `ylwjhfx` 前端页面引用静态资源时已规范使用了查询参数版本号（如 `style.css?v=3.2.0.280`、`app.js?v=3.2.0.280`）。
  - **运作逻辑**：静态资源即使设置了 7 天甚至 30 天强缓存，一旦系统发版发布新版本（例如版本号变为 `v=3.2.0.281`），由于 `index.html` 绝不缓存，用户刷新获取到新 HTML，浏览器识别到静态资源 URL 发生改变，**会立即主动拉取最新文件，完全杜绝旧代码残留**。

## 3. 落地实施方案与技术选型

本方案提供两种落地实施路径，**首选方案一（网关反代层落地，原业务项目代码 0 修改）**，方案二作为应用层兜底。

```
                    [ 浏览器发起请求 ]
                            │
               ┌────────────┴────────────┐
               ▼                         ▼
      【请求 index.html / API】      【请求 static (CSS/JS/Vendor)】
               │                         │
     [ no-store 穿透回源 ]       [ 检查 URL 带版本号: ?v=3.2.0.xxx ]
               │                         │
               │                   ┌─────┴────────────────┐
               │                   ▼ (首次访问)            ▼ (再次访问)
               │          [ Gzip 压缩传输 (削减72%) ]    [ 命中浏览器/CDN 强缓存 ]
               │          [ 写入 max-age=7天 / 30天 ]    [ 耗时 < 50ms 秒开 ]
               │                   │
               └─────────┬─────────┘
                         ▼
             【CT105 Lucky / CT160 反代网关】
                         │ (内网千兆 1ms)
                         ▼
             【3017 ylwjhfx 后端 Uvicorn】
```

### 3.1 方案一：CT105 Lucky / 网关层开启压缩与缓存（强烈推荐，业务代码 0 侵入）
* **实施位置**：`10.10.10.5` Lucky 网关 或 CT160 统一接入反代服务。
* **规则配置**：
  1. **Gzip 动态压缩**：
     - 启用类型：`text/html`, `text/css`, `application/javascript`, `application/json`, `image/svg+xml`。
     - 最小压缩阈值：`1024 字节`（小于 1KB 的短响应不压缩，避免无效消耗 CPU）。
     - 压缩等级：`Level 5`（兼顾极高压缩比与极低 CPU 占用，1MB JS 压缩仅耗时约 2ms）。
  2. **静态资源 Cache-Control 注入**：
     - 匹配规则 `/vendor/*`：注入 `Cache-Control: public, max-age=2592000, immutable`（30天，基础依赖库）。
     - 匹配规则 `*.css`, `*.js`（排除 API 路径）：注入 `Cache-Control: public, max-age=604800`（7天）。
     - 匹配规则 `/`、`*.html` 及 `/api/*`：强制注入 `Cache-Control: no-cache, no-store, must-revalidate`。
* **优势**：
  - 3017 项目 Python 源码、数据库、配置**一字不改**。
  - 未来新增 3012、3029、3041 等其他业务系统接入该反代时，全量自动继承加速能力。

### 3.2 方案二：FastAPI 应用层标准增强（改动仅 2 行）
若网关层调整受限，可直接在 `3017-美团供应链-ylwjhfx/backend/main.py` 中引入 FastAPI / Starlette 官方原生中间件：

```python
# backend/main.py
from fastapi.middleware.gzip import GZipMiddleware

# 仅需添加此行，只对大于 1000 字节的响应进行 Gzip 压缩
app.add_middleware(GZipMiddleware, minimum_size=1000)
```

静态文件缓存头定制：
```python
# 针对 StaticFiles 挂载注入静态缓存响应头（HTML与API除外）
class CachedStaticFiles(StaticFiles):
    def is_not_modified(self, response_headers, request_headers) -> bool:
        return super().is_not_modified(response_headers, request_headers)

    async def get_response(self, path: str, scope):
        response = await super().get_response(path, scope)
        if not path.endswith(".html"):
            response.headers["Cache-Control"] = "public, max-age=604800"
        else:
            response.headers["Cache-Control"] = "no-cache, no-store, must-revalidate"
        return response
```

## 5. 实施演进步骤 (Micro-steps)

2. 校验测试环境客户端（Chrome、Safari、移动端）渲染无报错。

### Step 2: 网关层配置与热重载 (先备份后重载)
1. 备份 Lucky 反代或 Nginx 现有配置文件。
2. 配置 Gzip 压缩参数与 `Cache-Control` 分流规则（严格排除 `/api/` 与 `index.html`）。
3. 平滑重载网关服务（不中断业务长连接）。

### Step 3: 全链路验证与防回滚验收
1. 使用 `curl -sI -H "Accept-Encoding: gzip"` 检查 `https://ylwjhfx.808608.xyz/vendor/echarts/echarts.min.js`，确认返回包含 `Content-Encoding: gzip` 与 `Cache-Control: public, max-age=...`。
2. 检查 `https://ylwjhfx.808608.xyz/api/daily-summary`，确认**绝不包含**静态缓存头，严格维持动态实时拉取。
3. 检查 `https://ylwjhfx.808608.xyz/` 首页，确认 `Cache-Control: no-cache, no-store` 依然生效。
4. 打开外部真实移动网络，验证 `https://ylwjhfx.808608.xyz` 页面图表展示、对账表格、进销存操作完全正常。

### Step 4: 回滚预案 (Emergency Rollback)
* 若发现任何老旧客户端展示异常，**10 秒内一键还原网关配置**，关闭 Gzip 与静态缓存，流量即刻恢复为现有的明文直传模式，系统 100% 原样恢复。
